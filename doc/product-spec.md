# プロダクト仕様書（壁打ちまとめ）

本ドキュメントは、タスク＆Todo管理Webアプリに関する要件壁打ちの結論をまとめたものです。  
概要レベルの記述は [requirements.md](./requirements.md) を参照してください。

**最終更新:** 2026-05-26

---

## 1. 背景・目的

- 既存ツールでは **バックログ（抱えている仕事）** と **今日の時間割** が連動しにくい。
- **ドッグフーディング（自己利用）** を最優先。将来はフリーミアムSaaSも視野。
- **GTD** の考え方を取り入れ、**Todoカレンダーを見れば今日やることがすぐわかる** ことを理想とする。
- カレンダーは **夕方の振り返りでだんだん埋まっていく** 運用を前提とする（朝から全枠埋めは不要）。

---

## 2. コアコンセプト

### 2.1 一気通貫の流れ

```
（任意）プロジェクト → タスク（リーフ/親） → Todo（日付・時間） → 作業時間計測
```

| 層 | 比喩 | 性質 |
|----|------|------|
| **プロジェクト** | 作業パッケージ / 案件の箱 | ストックの分類。Redmineの「チケット1件」に近いイメージで使うこともある |
| **タスク** | バックログ | 期限・見積・実績を持つ。実行単位は **リーフ** |
| **Todo** | 今日（または指定日）のコミット | タイムライン上の予定。計測は **必ずTodo経由** |
| **作業セッション** | 実績の本体 | 開始・終了時刻。タスク（リーフ）に分単位で集計 |

### 2.2 タスクとTodoの分離

- **タスク** = 抱えている仕事（ストック）
- **Todo** = いつやるか決めたもの（フロー）。「今日やる」とコミットしたものだけが今日画面に出る

### 2.3 GTDとの対応

| GTD | 本ツール |
|-----|----------|
| インボックス | **Inbox**（システムプロジェクト） |
| 次のアクション | **リーフタスク** |
| プロジェクト（複数ステップの成果） | **プロジェクト** + 親タスク（任意） |
| カレンダー / 今日やること | **Todoタイムライン** |
| いつかやる | バックログのリーフ（Todo未作成） |

**原則:** バックログのタスクを **自動でカレンダーに載せない**。警告は出すが、配置はユーザーが手動で行う。

## 3. プロジェクト

### 3.1 基本

- **1段のみ**（サブプロジェクトは採用しない）
- タスクの `project_id` は **NULL可**（プロジェクトなしタスクを常用）
- **付け替え可能**（Inbox → 問合せ → 案件 → なし、など）

### 3.2 システムプロジェクト（初期データ）

| 名前 | 用途 |
|------|------|
| **Inbox** | 未整理・とりあえず・該当なしのデフォルト置き場 |
| **問合せ・差し込み** | 性質がはっきりした問合せ・割込 |

- `is_system: true`（削除不可推奨）
- 新規リーフのデフォルト先は **Inbox** を推奨（プロジェクトなしも併用可）
- **ユーザー登録時**に Inbox・問合せ・差し込み を **そのユーザー用に自動作成**（システムプロジェクトのテンプレート投入）
- 同時に問合せ・差し込み配下へシステムリーフ **`（割込記録）`** を1件作成（割込計測の器）

### 3.3 属性（MVP）

| 属性 | 必須 | 説明 |
|------|------|------|
| `title` | ○ | |
| `status` | ○ | 未着手 / 進行中 / 完了 など |
| `description` | - | |
| `category` / `group` | - | 「クライアントA」「社内改善」などの束ね（階層の代わり） |
| `color` | - | UI用 |
| `archived_at` | - | |
| `is_system` | - | Inbox等 |

- **Redmine連携は行わない**（手動登録のみ）。`redmine_*` フィールドは当面不要。

### 3.4 整理方針（サブプロジェクト vs サブタスク）

- **サブタスク（タスク親子）を採用**。プロジェクト階層は使わない。
- 細かい分解はタスク側。プロジェクトは粗いラベル／箱。

## 4. タスク

### 4.1 親タスクとリーフ

| 種類 | 条件 | Todoに配置 | 計測 |
|------|------|------------|------|
| **親タスク** | 子タスクを持つコンテナ | **不可** | 不可（実績は子に集約） |
| **リーフタスク** | 子なし | **可** | 可（Todo経由） |

- 見積・期限・実績は **リーフ** に持つ（親は子の合計を表示）
- 親子の深さは **2段まで**（親 → 子リーフのみ）を推奨

### 4.2 属性

| 属性 | 説明 |
|------|------|
| `title`, `description`, `status` | 基本 |
| `due_date` | 期限（必須とするかは実装時に最終判断） |
| `estimate_minutes` | 見積（分または時間表示） |
| `actual_minutes` | 実績合計（セッション集計） |
| `project_id` | NULL可。付け替え可 |
| `parent_id` | NULLならリーフ or 単独タスク |

### 4.3 登録パターン

| パターン | 手順 |
|----------|------|
| **A. 案件** | プロジェクト作成 → （任意）親タスク → リーフ → Todo |
| **B. 問合せ・雑務** | 問合せ用プロジェクト or Inbox にリーフ → Todo |
| **C. 単発** | プロジェクトなしリーフ → Todo |
| **D. 割込計測（今日）** | タイムライン `+` からラベル付き実績を即記録（タスクは増やさない） |

### 4.4 警告（自動配置はしない）

例:

- 期限が近いのに今週・今日のTodoがない
- プロジェクト期間内なのにセッションが一度もない
- 同じTodo/タスクが何度も繰越されている

→ バックログ・プロジェクト画面で通知。**カレンダーへは載せない。**

## 5. Todo（タイムライン）

### 5.1 役割

- 指定日（基本は **今日**）の「やること」へのコミット
- **ホーム画面 = その日のTodoカレンダー**
- 計測（`work_sessions`）は **`todo_id` 必須**

### 5.2 カレンダーUI

| 項目 | 仕様 |
|------|------|
| 目盛り | **15分**（表示） |
| 操作スナップ | **5分 or 10分** |
| Todoの長さ | **可変**（`planned_minutes`） |
| デフォルト | 通常 **30分** |
| 重なり | MVPは **警告または禁止** |
| **計画と実績** | **二層表示**（§5.6）。Todo=計画、Session=実績 |

「30分で考える」= 計画の **デフォルトプリセット**。固定30分枠のみではない。

### 5.6 計画と実績の二層表示

タイムライン上で **Todo（計画）** と **work_sessions（実績）** を同時に表示し、一目で「予定 vs 実際」を把握する。

| 層 | データ | 見た目 | 操作 |
|----|--------|--------|------|
| **計画** | Todo（`scheduled_start` + `planned_minutes`） | 点線枠・半透明。ラベルに「計画」 | DnD・リサイズ・▶計測開始 |
| **実績（完了）** | Session（`started_at`〜`ended_at`） | 左アクセント線 + 塗り（半透明）。`duration_minutes` 表示 | クリック → 開始・終了時刻修正 |
| **実績（計測中）** | Session（`ended_at` NULL） | 塗り + 脈動。**開始時刻からリアルタイムに伸びる** | 上部 SessionBar で停止 |

**表示ルール**

- 指定日のセッション: その日の **00:00〜23:59（ローカル）に `started_at` がある** ものを表示
- 1 Todo に複数セッションがあっても、それぞれ `started_at` 位置に描画
- 計画ブロックと実績バーは **重ねて表示**（z-index: 実績 < 計画）。時刻がずれても両方見える
- 画面下の「最近のセッション」リストは **廃止**（実績はタイムライン上で確認・修正）

**凡例（タイムラインヘッダー付近）:** 点線 = 計画 / 塗り = 実績

### 5.3 割込計測（旧・快速追加）

横入りの問合せ対応など、**先に実績だけ記録**したいときの入口。

- タイムライン上の `+` → ラベル入力 → **即計測開始**（SessionBar + 実績バー）
- **個別タスクは作らない**。DB 上はシステムリーフ `（割込記録）`（問合せ・差し込み）+ `is_ad_hoc` Todo に紐づく
- `work_sessions.label` に表示名を保持（UI・CSV はラベル優先）
- タイムライン左の **計画ブロックは出さない**（実績のみ）
- バックログには `（割込記録）` を **表示しない**
- 停止時、紐づく ad-hoc Todo は `done` にする（繰越対象外）
- 後から本格的なタスク化が必要なら、通常のタスク登録で対応（専用昇華 UI は持たない）

### 5.4 一日のリズム

| 時間帯 | カレンダー |
|--------|------------|
| 朝 | スカスカでも可。確定分＋未配置 |
| 日中 | 配置・割込計測・計測で埋まっていく |
| 夕方 | 振り返り。**明日を準備** で明日の土台を作る |

## 6. 作業時間計測

### 6.1 基本方針

- **計測単位は分・時間**。ポモドーロ数での管理は **しない**。
- **ポモドーロタイマー** は長時間タスク向けの **任意機能**（完了時も分に換算してセッション追加）。

### 6.2 work_sessions

| フィールド | 説明 |
|------------|------|
| `task_id` | リーフ（必須）。割込計測は `（割込記録）` |
| `todo_id` | 必須 |
| `label` | 割込計測の表示名（任意。ある場合 UI・CSV でタスク名より優先） |
| `started_at`, `ended_at` | 終了NULL = 計測中 |
| `duration_minutes` | 算出または確定値 |
| `source` | `timer` / `manual` / `edited`（任意） |

### 6.3 操作

| 操作 | 説明 |
|------|------|
| **開始 / 停止** | 基本。同時に動くセッションは **1つのみ** |
| **事後修正** | 停止忘れ等 → **開始・終了時刻**を編集 |
| **割込計測** | ラベル入力 → 即タイマー開始（計画ブロックなし） |
| **手動追加** | 計測忘れ → **開始・終了必須** で過去セッション追加（該当Todoを指定） |

「分だけ」入力（時刻なしで分数のみ）は **採用しない**。

### 6.4 タイムライン上の実績表示

- 完了セッション: `started_at` / `ended_at`（または `duration_minutes`）からバーの位置・高さを算出
- 計測中: SessionBar と同期し、1秒ごとにバー高さを更新
- 修正入口: 実績バークリック → 開始・終了時刻修正モーダル（§6.3 事後修正）

### 6.5 集計

- タスクの `actual_minutes` = 紐づくセッションの合計
- ロールオーバー後も **セッション・実績はタスクに残る**
- タスクのステータスは未完了のまま維持（完了は手動）

## 7. 明日を準備（繰越・定期の統合）

### 7.1 概要

夕方の振り返りで実行する **単一ボタン `[明日を準備]`**。

1. 今日の **未完了Todo**（繰越対象を選択）
2. **定期ルール**のうち、翌日に該当するもの（選択）
3. 翌日のカレンダーへ反映 → ユーザーが **手動調整**

**自動0時処理はしない。**

### 7.2 配置の優先順位（確定: 定期優先）

翌日タイムラインへの配置順:

| 順序 | 対象 | 配置方法 |
|------|------|----------|
| **1** | **時刻ありの定期** | 指定時刻に `planned_minutes` で配置 |
| **2** | **時刻なしの定期** | **30分仮配置**（空きスロットに順に） |
| **3** | **今日の残りTodo（繰越）** | **30分仮配置**（空きスロットに順に） |

起点: ユーザー設定の **翌日始業時刻**（例 09:00）。

入りきらない場合: 警告を表示。未配置へは **自動では入れない**（手動で調整）。

### 7.3 繰越のデータルール

- 繰越の選択単位は **タスク**（同一タスクの当日 pending Todo はまとめて対象）
- 同一タスクに複数 Todo がある場合、翌日は **1件に合算**（`planned_minutes` の合計）して複写
- 翌日に **新規Todo** を作成（同一リーフタスクに紐づけ）。配置は §7.2 の **30分仮配置**（始業時刻から空きスロット）
- 今日側の対象 Todo はすべて `status = rolled_over` で非アクティブ化（重複計測・再編集防止）
- **当日のタイムラインには `rolled_over` の計画ブロックを読み取り専用で残す**（振り返り用。移動ではなく複写として見えること）
- `rolled_from_todo_id` は代表 Todo（同一タスク内の先頭）を記録（任意）

### 7.4 定期ルール（第一弾）

| 繰り返し | 条件 |
|----------|------|
| **毎日** | 常に翌日に生成 |
| **平日** | 翌日が月〜金のときのみ |
| **毎週○曜** | 翌日が指定曜日のときのみ |

| 属性 | 説明 |
|------|------|
| `recurrence` | `daily` / `weekdays` / `weekly` |
| `day_of_week` | weekly時のみ |
| `task_id` | 紐づくリーフ |
| `default_duration_minutes` | デフォルト30、変更可 |
| `scheduled_time` | 任意。NULLなら30分仮配置 |
| `enabled` | on/off |

- **1ルール × 1日 = Todo最大1件**（重複生成防止）
- 祝日スキップは v2

### 7.5 確認画面（UI案）

```
明日を準備 — 2026年5月26日（火）

■ 定期（明日に該当）  … デフォルトON
■ 今日の残り（繰越）  … チェック選択

[キャンセル]  [明日のカレンダーに反映]
```

実行後 → **明日の日付** の今日画面へ遷移し、ブロックを手動調整。

## 8. 画面構成（目標）

```
┌─ グローバル ─────────────────────────────┐
│  ● 計測中: タイトル  00:12:34  [停止]     │  ← 常に1セッション
├─────────────────────────────────────────┤
│ 今日のタイムライン（主体）                  │
│  15分目盛り                               │
│  点線=計画 Todo / 塗り=実績 Session        │
├─────────────────────────────────────────┤
│ ▼ バックログ / Inbox（折りたたみ）          │
└─────────────────────────────────────────┘
```

- 起動時デフォルト: **今日のTodoカレンダー**
- リーフのみDnD可能。親タスクは見出しのみ
- セッション一覧は **タイムライン上の実績バー** のみ（画面下の「最近のセッション」は持たない）

## 9. データモデル（概念）

> **詳細設計:** カラム定義・ER 図・RLS・マイグレーション順序は [database-schema.md](./database-schema.md) を参照。

全業務テーブルに `user_id`（`auth.users.id`）を持ち、**Supabase RLS** でログインユーザー自身の行のみ読み書き可能にする。

```
profiles（任意）
  id (= auth.users.id), email, display_name, work_day_start (例 09:00), ...

projects
  id, user_id, title, status, category, color, is_system, archived_at, ...

tasks
  id, user_id, project_id (nullable), parent_id (nullable),
  title, status, due_date,
  estimate_minutes, actual_minutes,
  is_leaf (derived or explicit), ...

todos
  id, user_id, task_id (NOT NULL), date,
  scheduled_start (nullable), planned_minutes,
  status, recurring_rule_id (nullable),
  rolled_from_todo_id (nullable), ...

work_sessions
  id, user_id, task_id, todo_id (NOT NULL),
  started_at, ended_at, duration_minutes, source, ...

recurring_rules
  id, user_id, task_id, recurrence, day_of_week,
  scheduled_time (nullable), default_duration_minutes, enabled, ...
```

**アクティブセッション:** `work_sessions.ended_at IS NULL` がユーザーごとに最大1件（DB制約またはアプリで保証）。

## 11. 技術スタック（確定）

| 層 | 技術 | 備考 |
|----|------|------|
| **ホスティング** | [Vercel](https://vercel.com/) | Next.js App Router のデプロイ。プレビュー環境 |
| **フロント** | Next.js (App Router) / React / Tailwind CSS | Server Components + Client Components |
| **DB** | [Supabase](https://supabase.com/) Postgres | マイグレーションは Supabase CLI / SQL |
| **認証** | Supabase Auth | **Google OAuth** + **メール**（登録・ログイン） |
| **API・データアクセス** | Supabase Client（`@supabase/supabase-js`）+ SSR（`@supabase/ssr`） | Server Actions / Route Handlers から RLS 付きで操作 |
| **DnD** | `@hello-pangea/dnd` 等 | |
| **将来課金** | Stripe | フリーミアム時。`profiles` 等に `stripe_customer_id` |

**採用理由（要約）:** Next.js との相性、Postgres + RLS によるマルチユーザー隔離、Google/メール認証の設定容易さ。Cloudflare（Workers + D1）は検討したが、本プロジェクトでは不採用。

### 11.1 認証

| 方式 | 方針 |
|------|------|
| **Google OAuth** | Supabase Dashboard で Google プロバイダを有効化 |
| **メール** | Email プロバイダ有効化（確認メール・パスワードリセット）。MVP では **メール + パスワード** または **マジックリンク** のいずれか（実装時に選択） |
| **セッション** | Supabase が発行する JWT。Cookie ベース（`@supabase/ssr` で App Router と連携） |
| **保護ルート** | 未ログイン時は `/login` へ。ミドルウェアでセッション更新 |

サインアップ直後の処理（DB trigger またはアプリ）:

- `profiles` 行の作成（任意）
- システムプロジェクト **Inbox**・**問合せ・差し込み** の作成
- ユーザー設定のデフォルト（翌日始業時刻など）

### 11.2 アーキテクチャ（概略）

```
ブラウザ
  → Next.js（Vercel）
       ├─ Server Components / Server Actions
       └─ Supabase Client（anon key + ユーザ JWT）
            → Postgres（RLS: auth.uid() = user_id）
            → Supabase Auth（Google / Email）
```

- **サービスロールキー**はサーバー側の管理処理のみ（バッチ等）。通常の CRUD は **anon + ユーザセッション** と RLS。
- 「明日を準備」など複数行更新は **Server Action** または **Postgres 関数（RPC）** でトランザクション化を検討。

### 11.3 環境・リポジトリ

| 環境 | 用途 |
|------|------|
| ローカル | `next dev` + Supabase local（CLI）または開発用リモートプロジェクト |
| Vercel Preview | PR ごと。Supabase の staging プロジェクトと接続推奨 |
| Vercel Production | 本番。Supabase production |

環境変数（例）: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`（Vercel に設定。サービスロールはサーバーのみ）。

## 14. 開発着手時の推奨順序

1. Supabase プロジェクト作成・Vercel 連携・環境変数
2. スキーマ + **RLS**（`user_id`、全テーブル）+ サインアップ時 Inbox 作成
3. **Supabase Auth**（Google + メール）+ ログイン画面 + ミドルウェア
4. 今日カレンダー + リーフのDnD + 未配置
5. セッション（開始/停止、修正、手動追加）
6. 割込計測 / プロジェクト付け替え
7. 明日を準備（繰越30分）
8. 定期ルール + 明日を準備への統合
9. 警告表示
10. ポモタイマー（任意）
